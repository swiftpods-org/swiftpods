# SwiftPods — техническая спецификация

**Версия документа:** 0.9<br>
**Дата:** 15 октября 2026 года<br>
**Статус:** проект требований; реализация и результаты тестирования этим документом не утверждаются.  
**Главный приоритет:** миграция с CocoaPods без переписывания Podfile, podspec и пользовательских Ruby-хуков. Ruby устанавливается отдельно; SwiftPods не включает интерпретатор в свою поставку.

**Изменение 0.8 / NATIVE-ENGINE-001:** ядро SwiftPods полностью реализуется самостоятельно на Swift. CocoaPods 1.17.0 является только референсом наблюдаемого поведения и используется в изолированных сравнительных тестах. Запрещена runtime-зависимость от его ядра, resolver, downloader и генератора проектов. Внешний CRuby исполняет пользовательские Podfile, podspec, helpers и hooks через собственный адаптер SwiftPods. Решение отменяет архитектурные положения 0.4–0.7 о поставке готового Ruby-ядра. Полное покрытие контрактов ниже является целью; наличие адаптера или успешной fixture не доказывает совместимость всего API.

**Изменение 0.9 / INPUT-COMPAT-001:** обязательный контракт — совместимое чтение и интерпретация существующих входных данных. Ошибки CocoaPods не наследуются. SwiftPods может использовать более простую реализацию, исправлять ошибки и улучшать результат при сохранении смысла корректных Podfile, podspec, helpers, поддерживаемых hooks и lockfiles. Совпадение внутренней архитектуры и ошибочных результатов референса не требуется.

## 1. Назначение и основные решения

SwiftPods — поддерживаемый преемник CocoaPods для управления нативными зависимостями Apple-платформ. Название не ограничивает языки библиотек: должны поддерживаться Swift, Objective-C, Objective-C++, C и C++, исходные проекты и готовые бинарные SDK.

SwiftPods сохраняет язык CocoaPods. `Podfile` и `.podspec` остаются исполняемым Ruby-кодом с прежним DSL; `.podspec.json` сохраняется как альтернативный вход. Обязательных `SwiftPods.yml`, `Swiftfile`, `Package.swift` или `.swiftpodspec` не появляется.

Swift реализует CLI, resolver, работу со spec repositories, загрузку и кеш исходников, lockfile, генерацию и интеграцию Xcode-проектов, диагностику и recovery. Ruby исполняет только пользовательский DSL, helpers и hooks через собственный адаптер; независимый Ruby-процесс сохраняется на время установки для сохранения closures и их состояния. Xcode/SDK, Git, CMake и инструменты пользовательских build scripts остаются требованиями соответствующих workflows.

SwiftPM не используется как универсальный исполнитель podspec. Поддержка нативных Swift-пакетов добавляется отдельно и не меняет семантику существующих pod-зависимостей.

Публичный план CocoaPods предусматривает перевод Trunk в режим read-only 2 декабря 2026 года; это не означает прекращения работы самого клиента или частных spec-репозиториев. SwiftPods должен уметь работать без публикации через Trunk. Дата в плане может быть изменена его авторами. [R1]

## 2. Нормативная база и терминология

Слова «ДОЛЖЕН», «НЕ ДОЛЖЕН» и «ДОПУСКАЕТСЯ» задают обязательные требования, запреты и разрешённые варианты реализации.

**Профиль совместимости** — ревизия собственного Swift-движка и Ruby-адаптера, ревизии изолированного референса для тестов, политика внешнего CRuby и явно импортированные пользовательские gems. Профиль задаёт наблюдаемое поведение. SwiftPods не выбирает глобальные gems. Базовая проверенная версия CRuby — 3.4.11; допускается CRuby >= 3.4.11, < 3.5.0 с ABI 3.4.0 и архитектурой поставки. Фактически проверенные версии Ruby записываются в evidence отдельно.

Базовый профиль проекта и сравнительный референс: CocoaPods **1.17.0**. Такой релиз присутствует в официальном репозитории на дату подготовки документа. Онлайн-справочник DSL при этом обозначен как 1.16.1; для трактовки входных данных используются исходники и тесты выбранного релиза. Подтверждённые ошибки референса не задают обязательный результат SwiftPods. [R2, R3, R4]

Lockfile из 1.16.2 входит в обязательный корпус миграционных тестов. Это не означает автоматической побайтовой эмуляции всех старых версий CocoaPods. Дополнительные профили поддерживаются только после отдельной проверки.

Каждый релиз SwiftPods ДОЛЖЕН публиковать `compatibility.json` с версиями, полными commit SHA собственного кода и upstream, toolchain, digest launcher/поставляемых файлов, явных пользовательских gem-профилей, политикой внешнего Ruby, фактической версией Ruby при проверках, минимальной macOS, архитектурой и известными ограничениями. Release manifest перечисляет архивы, SHA-256 и OS/architecture. Строго воспроизводимый CI закрепляет release manifest, установщик и внешнюю версию Ruby; обновление Ruby Homebrew не считается проверкой нового сочетания.

Исходные ревизии базового эталона: CocoaPods `5493bfd201a3be9325123cfa59142760afe198d7`, CocoaPods-core `f14b9a21f3aacd771c1eb9b099910d33a6d2cce0`. Изменения собственного движка и тестового референса фиксируются отдельно; наличие этих SHA не является доказательством готовности поставки или прохождения тестов.

## 3. Объём совместимости

### 3.1. Обязательный контракт

**SP-COMPAT-001.** Существующий корректный `Podfile`, использующий поддерживаемое окружение и API базового профиля, принимается без изменений исходного текста.

**SP-COMPAT-002.** Поддерживаются оригинальные `.podspec` и `.podspec.json`; автор библиотеки не обязан публиковать отдельный формат SwiftPods.

**SP-COMPAT-003.** Сохраняется смысл корректных входных данных: ограничения версий, наследование target, выбор subspec, источник зависимости, параметры линковки, ресурсы и публичный API поддерживаемых пользовательских хуков. Конкретный алгоритм, структура сгенерированного проекта, диагностика и вспомогательные артефакты могут быть проще или лучше референса. Изменение реализации не разрешает молча игнорировать входные настройки, терять пользовательские правки или нарушать закреплённые зависимости.

**SP-COMPAT-004.** Совместимость проверяется не только успешным чтением файлов, но и сборкой, тестами, содержимым приложения и повторной установкой.

**SP-COMPAT-005.** Неизвестная конструкция или неподдерживаемая возможность НЕ ДОЛЖНА молча игнорироваться. Инструмент выдаёт ошибку с местоположением и причиной либо явно документированное предупреждение. Улучшенная диагностика допускается; предупреждение не подменяет обязательный эффект входной настройки успешным no-op.

**SP-COMPAT-006.** Ошибки и внутренние ограничения CocoaPods НЕ ДОЛЖНЫ воспроизводиться ради буквального совпадения. Исправление или упрощение проверяется на неизменённом входе и на корректном результате, отражается в реестре контракта и сохраняется в отчёте как подтверждённое улучшение. Непроверенное расхождение не считается улучшением автоматически. Например, BridgeSupport ДОЛЖЕН получать существующий заголовок и создавать метаданные, даже когда референс ошибочно передаёт отсутствующий файл.

### 3.2. Границы обещания

Полный Ruby DSL не означает совместимость с любым внешним окружением. Скрипт может зависеть от конкретной версии Ruby, native gem, расположения `/usr/bin/ruby`, системной утилиты, monkey patch приватного метода или результата сетевого запроса.

Такие зависимости не переписываются автоматически. Предусмотрены проверка окружения, явный профиль пользовательских gems/plugins и отдельные compatibility fixtures. `Gemfile` и `.ruby-version` не должны молча подменять выбранный внешний runtime. Скрипты, проверяющие имя executable или конкретную версию инструмента, требуют отдельной оценки.

Обещание «любой Podfile из интернета гарантированно работает» не используется. Цель стабильного релиза — совместимые форматы и смысл существующих входных данных без обязательного переписывания поддерживаемых manifests и hooks. Собственная реализация может быть проще и исправлять ошибки референса; зависимость от его ошибочного результата или приватного внутреннего устройства не входит в безусловное обещание.

## 4. Пользовательский сценарий и миграция

Для обычного проекта меняется только команда:

```bash
# Before
pod install

# After
swiftpods install
```

`swiftpods install` автоматически обнаруживает `Podfile`, существующий `Podfile.lock`, установленный `Pods` и пользовательский workspace. Отдельная команда миграции не обязательна.

Первый запуск НЕ ДОЛЖЕН обновлять версии библиотек только потому, что сменился менеджер. Он также не должен удалять весь `Pods`, создавать новый workspace вместо явно заданного или переписывать пользовательские файлы для ребрендинга.

Предварительная проверка:

```bash
swiftpods migrate --check
swiftpods doctor --static
swiftpods install --deployment
```

Это проектируемые команды SwiftPods, а не команды уже выпущенного продукта.

`migrate --check` и `doctor --static` не исполняют Ruby, hooks или scripts и не загружают плагины. Они анализируют доступные метаданные; динамические части и свойства, требующие исполнения или сборки, помечают как непроверенные. Они не выдают заключение о полной совместимости без исполнения и сборки.

Для проверки реального поведения пользователь выполняет установку в доверенной рабочей копии или изолированной CI-среде. Podfile, Ruby podspec, hooks, gems, `prepare_command` и build-time scripts могут иметь побочные эффекты. Полноценный install не считается безопасным статическим анализом или изолированным sandbox.

## 5. Язык Podfile

### 5.1. Исполнение Ruby

Podfile исполняется настоящим внешним CRuby runtime. Самостоятельный parser «похожего Ruby», преобразование регулярными выражениями или обязательное предварительное преобразование в JSON запрещены как основа compatibility-режима. Собственный Ruby-интерпретатор на Swift не является частью проекта.

Такое решение соответствует природе исходного формата: CocoaPods исполняет содержимое Ruby Podfile, а не рассматривает его только как декларативные данные. [R5]

Сохраняются конструкции Ruby: переменные, массивы и хеши, блоки, методы и классы, условия и циклы, интерполяция, heredoc, исключения, `ENV`, `File`, `Dir`, `require`, `require_relative`, `load` и загрузка gems в выбранном зафиксированном окружении.

Относительные пути, текущий каталог, `__FILE__`, `__dir__`, кодировка, порядок выполнения и номера строк в ошибках должны соответствовать базовому профилю. Нельзя кэшировать результат вычисления Podfile только по его тексту: на результат могут влиять другие файлы и окружение.

### 5.2. Сохраняемый DSL

Поддерживается весь DSL базового профиля, включая значения по умолчанию, допустимые типы аргументов и ошибки. Список ниже группирует требования, но не ограничивает их. Это контракт будущей реализации; подтверждённое покрытие публикуется отдельно:

| Группа | Обязательное поведение |
|---|---|
| Зависимости | `pod`, ограничения версий, subspec, `podspec`, внешние и локальные источники |
| Структура | `target`, `abstract_target`, `abstract!`, `inherit!`, вложенность и область действия |
| Проект | `platform`, `project`, `workspace`, mapping пользовательских build configurations |
| Сборка | `use_frameworks!`, `use_modular_headers!`, warning controls, Swift version requirements |
| Установка | `install! 'cocoapods'` со всеми опциями профиля, включая режим без интеграции и multiple projects |
| Расширение | `plugin`, четыре Podfile hook, `script_phase`, проверки Bundler в выбранном окружении |

Примеры перечисленных групп и актуальные правила DSL определяются официальной справкой и исходниками выбранного профиля. [R3, R6]

Значение `install! 'cocoapods'` остаётся допустимым: пользователь не обязан заменять его на `swiftpods`. Старые aliases поддерживаются ровно в той мере, в которой их поддерживает эталон; удалённый API не объявляется работающим ради формального принятия файла.

### 5.3. Контрольный пример

Названия `GameCore`, target и пути в примере условные; это fixture для проекта, где соответствующие файлы существуют.

```ruby
source 'https://cdn.cocoapods.org/'

platform :ios, '16.0'
project 'build/ios/Game.xcodeproj'
workspace 'Game'

install! 'cocoapods',
  :deterministic_uuids => true,
  :generate_multiple_pod_projects => false

use_frameworks! :linkage => :static

require_relative 'scripts/ios_dependencies'

target 'Game' do
  pod 'GameCore', :path => './Modules/GameCore'

  if ENV['ENABLE_ADS'] == '1'
    add_advertising_dependencies
  end

  target 'GameTests' do
    inherit! :search_paths
  end
end

post_install do |installer|
  installer.pods_project.targets.each do |target|
    next unless target.name.start_with?('GameCore')

    target.build_configurations.each do |configuration|
      configuration.build_settings['CLANG_CXX_LANGUAGE_STANDARD'] = 'c++17'
    end
  end
end
```

Этот файл не преобразуется и не форматируется заново при миграции. Перенос существующих helper-функций и hooks в новый API не требуется для поддерживаемого профиля.

## 6. Совместимость Podspec

**SP-SPEC-001.** Сохраняются `Pod::Spec.new` и объектная модель `Pod::Specification`. JSON-форма является альтернативным входом, а не обязательной заменой Ruby.

**SP-SPEC-002.** Реестр атрибутов и их наследование берутся из выбранного профиля. Он включает метаданные; source; платформенные ограничения; зависимости; subspec/default subspec; test spec и app spec; исходники и заголовки; module map; resources и resource bundles; vendored библиотеки и frameworks; compiler/linker settings; ARC; xcconfig; Swift versions; prepare command и script phases. [R4, R7]

**SP-SPEC-003.** Семантика glob, исключений файлов, публичных/приватных/project headers, платформенных overrides и default subspec должна сохраняться. Недостаточно прочитать поля и затем передать только часть из них другой системе сборки.

**SP-SPEC-004.** Для ресурсов сохраняются имена bundle, пути, локализация и правила копирования. Изменение способа поиска ресурсов библиотекой недопустимо без явной миграции.

**SP-SPEC-005.** `prepare_command` выполняется в предусмотренный CocoaPods 1.17.0 момент, включая локальные dependencies через `:path`. В закреплённом эталоне `PodSourceInstaller#install!` вызывает `PodSourcePreparer#prepare!` для local pod; это происходит до Podfile `pre_install`. SwiftPods не отключает этот вызов и не добавляет собственные повторные вызовы. Поведение первой, повторной и deployment-установки сравнивается с эталоном. Изменения локальных файлов, явно сделанные `prepare_command` или hooks, являются побочными эффектами пользовательского кода и не выдаются за полностью откатываемые изменения менеджера. [R15]

Пример совместимого podspec:

```ruby
Pod::Spec.new do |spec|
  spec.name = 'GameCore'
  spec.version = '1.0.0'
  spec.summary = 'Native game runtime components.'
  spec.homepage = 'https://example.invalid/gamecore'
  spec.license = { :type => 'MIT', :file => 'LICENSE' }
  spec.author = { 'Example Team' => 'dev@example.invalid' }

  spec.source = {
    :git => 'https://example.invalid/gamecore.git',
    :tag => spec.version.to_s
  }

  spec.ios.deployment_target = '16.0'
  spec.source_files = 'Sources/**/*.{h,hpp,c,cpp,m,mm}'
  spec.public_header_files = 'Sources/Public/**/*.h'
  spec.requires_arc = true
  spec.libraries = 'c++'

  spec.pod_target_xcconfig = {
    'CLANG_CXX_LANGUAGE_STANDARD' => 'c++17'
  }

  spec.resource_bundles = {
    'GameCoreResources' => ['Resources/**/*']
  }
end
```

URL в этом примере намеренно демонстрационные. Новые обязательные атрибуты для SwiftPods не вводятся.

## 7. Хуки и Ruby API

### 7.1. Живые объекты

`pre_install`, `pre_integrate`, `post_install` и `post_integrate` сохраняют исходную модель исполнения.

В пределах одной команды существует один долгоживущий Ruby Compatibility Host. В нём живут Podfile, зарегистрированные closures, installer, sandbox, target и Xcode project objects. Нельзя вычислить Podfile, сериализовать его в JSON, завершить Ruby и затем считать, что hooks и runtime-состояние сохранены.

Используется самостоятельно реализованный совместимый API объектов Ruby, в том числе `Pod::Installer`, `Pod::Sandbox`, `Pod::Project`, `Xcodeproj::Project`, спецификации, aggregate targets и installation results. Изменения hooks должны передаваться в Swift-модель и сохраняться с прежней наблюдаемой семантикой. Неизвестные методы и неподдерживаемые операции отклоняются явно. Совместимость этого слоя требует отдельных behavioural tests; совпадение имён классов не является доказательством полного API.

### 7.2. Порядок выполнения

Нормативным является порядок installer базового профиля, включая отличие plugin hooks от одноимённых Podfile hooks. `post_install` изменяет Pods project до сохранения, а `post_integrate` наблюдает завершённую интеграцию пользовательского проекта. [R8]

Порядок нельзя менять ради упрощённой схемы «все pre до всех операций, все post после всех операций». Изменения hooks не теряются при дальнейшей обработке на Swift. На каждом этапе у объектной модели и файлов должен быть один владелец записи.

### 7.3. Plugins и private API

Методы и поля, на которые опираются существующие fixtures, сохраняются в выбранном профиле. Произвольные monkey patches и недокументированные внутренние API не получают безусловной межверсионной гарантии.

Диагностика различает документированный контракт, подтверждённую совместимость конкретной версии plugin и непроверенное вмешательство в private API. Отсутствующий необходимый plugin или несовместимый API не пропускается с успешным результатом.

### 7.4. Примеры CocoaPods hooks

Ниже демонстрационные примеры исходного CocoaPods workflow и сценарии проверки совместимости SwiftPods. Момент вызова определяется installer базового профиля. Примеры не утверждают, что реализация или тестирование уже завершены. [R8]

**`post_install`: изменить C++ standard конкретного pod перед сохранением Pods project.**

```ruby
post_install do |installer|
  installer.pods_project.targets.each do |target|
    next unless target.name == 'GameCore'

    target.build_configurations.each do |config|
      config.build_settings['CLANG_CXX_LANGUAGE_STANDARD'] = 'c++17'
    end
  end
end
```

Здесь используются циклы, условие и изменение Ruby-объектов Xcode-проекта. Аналогичные hooks применяют Swift version или другие build settings для отдельных targets/configurations.

**`pre_install`: проверить выбранные pod после скачивания и прервать установку.**

```ruby
pre_install do |installer|
  if installer.pod_targets.any? { |pod| pod.name == 'LegacySDK' }
    raise 'LegacySDK is not allowed in this project'
  end
end
```

**`post_integrate`: выполнить действие после интеграции пользовательского проекта.**

```ruby
post_integrate do |installer|
  File.write('pods-integration.txt', "Integration completed\n")
end
```

Этот пример пишет файл и имеет побочный эффект. `post_integrate` не следует считать уведомлением об успешном завершении абсолютно всех оставшихся этапов установки: в эталоне запись lockfiles происходит позднее. `pre_integrate` вызывается перед генерацией Pods project; это отдельная Ruby-точка расширения, порядок которой также проверяется.

Реальные интеграции также используют Ruby-хуки: [Flutter podhelper](https://github.com/flutter/flutter/blob/master/packages/flutter_tools/bin/podhelper.rb) вызывает `flutter_additional_ios_build_settings(target)` из `post_install`, а [шаблон React Native](https://github.com/react-native-community/template/blob/main/template/ios/Podfile) вызывает `react_native_post_install`. Эти helper-функции исполняют дополнительный Ruby-код в выбранном runtime. Их версии, внешние инструменты и обращение к API должны проверяться отдельными fixtures; поставка настоящего Ruby сама по себе не доказывает готовность интеграций Flutter или React Native.

## 8. Архитектура реализации

```text
SwiftPods CLI (Swift)
    |
    +-- Runtime and environment manager
    +-- Diagnostics and structured reporting
    +-- Cache and transport services
    +-- Installation journal and recovery
    |
    +-- Native Swift engine
    |       +-- Dependency resolver, sources and lockfile
    |       +-- Xcode project model, writer and integration
    |       +-- Resources, SDKs, test/app products and schemes
    |
    +-- Ruby DSL Host (external CRuby)
            +-- Own Podfile/podspec adapter and live hook object model
            +-- User helpers and explicitly configured plugins
            +-- Project operations delegated to the Swift engine
```

### 8.1. Разделение ответственности

Swift-слой владеет установкой зависимостей, resolver, источниками, кешем, lockfile, моделью проектов, генерацией и интеграцией Xcode. Ruby-слой владеет только исполнением DSL и пользовательских hooks; загрузка готового стороннего ядра запрещена.

Инструмент не зависит от глобальной команды `pod` или глобальных gems. Требуется отдельно установленный совместимый CRuby. Стороннее ядро используется только в изолированных reference-тестах и не входит в поставку. Обновления и тестирование собственного Swift-ядра являются ответственностью SwiftPods.

Ruby hooks работают с собственной живой объектной моделью, сохраняющей проверенные методы и идентичность объектов. Чтение и сохранение проектов выполняет Swift. Совместимость конкретного API подтверждается differential tests; приватный API не считается поддержанным по одному совпадению имени.

### 8.2. Граница процессов

IPC передаёт версионированные сообщения о задачах, событиях и диагностике. Ruby objects и closures не сериализуются через эту границу. Пользовательские `puts` и stderr отделяются от управляющего канала; произвольный текст script не должен повреждать протокол.

Отмена команды передаётся дочерним процессам. Падение Ruby, Swift или внешнего инструмента не должно отображаться как успешная установка. Нельзя повторно исполнять hooks автоматически после сетевого retry: повторяется только операция, для которой retry безопасен.

### 8.3. Переход к native-компонентам

Компонент можно заменить реализацией на Swift после прохождения differential tests относительно эталона. При изменении наблюдаемого поведения создаётся новый явно выбираемый профиль. Процент кода на Swift не является критерием совместимости или готовности релиза.

## 9. Ruby runtime, gems и Bundler

### 9.1. Стандартная поставка

SwiftPods поставляется как Swift executable и собственный Ruby DSL-адаптер. Стороннее Ruby-ядро, его gems и Xcodeproj не входят в production-поставку. Пользовательские gems подключаются отдельно через явный профиль; системный Bundler используется только для явного импорта такого профиля. Ruby executable, стандартная библиотека Ruby, OpenSSL и libyaml не включаются. Проверяются полнота, checksums, подписи release-артефактов и работа после переноса с внешним Ruby.

Обычная установка проекта требует внешнего CRuby >= 3.4.11, < 3.5.0 (ABI 3.4.0). Homebrew устанавливает ruby@3.4 отдельной зависимостью. `SWIFTPODS_RUBY` выбирает абсолютный путь явно; иначе проверяются стандартные Homebrew-пути, затем `ruby` из абсолютных PATH entries. У выбранного Ruby проверяются engine, version, ABI и architecture до исполнения проектного кода и начала installation journal. Несовместимый явный выбор не приводит к fallback. Глобальные Bundler/gems/pod и `sudo gem install` не требуются.

Релиз проверяется на Apple Silicon и Intel для опубликованной матрицы host-систем. Фактические внешние CRuby, Bundler, gems, Xcode, macOS и architecture фиксируются в evidence. Работа на будущих версиях не обещается. Минимальная macOS артефакта вычисляется по native load commands; native gems могут зависеть от объявленного внешнего Ruby.

### 9.2. Пользовательское окружение

Наличие Gemfile или `.ruby-version` не приводит к молчаливой подмене окружения. Диагностика показывает эффективные версии runtime, core и plugins и ограничения исходного проекта.

`swiftpods env import --gemfile Gemfile` создаёт отдельный профиль с пользовательскими gems. Импорт сохраняет зафиксированные версии, где они совместимы с ядром. Конфликт версии останавливает импорт; автоматическое обновление чужих gems запрещено.

Импорт исполняемого Gemfile выполняет доверенный Ruby-код и не является статическим чтением. Native gems должны соответствовать ABI/архитектуре runtime либо собираться в подготовленном окружении. Их совместимость нельзя гарантировать только по имени gem.

В v1 CLI не делает вид, что автоматически заменил пользовательский bundle. `bundle exec pod` продолжает выбирать executable из этого bundle, пока Gemfile или CI launcher не изменены явно. [R10]

### 9.3. Команда pod и plugins

Executable с именем `pod` допускается только как явный opt-in shim в выбранном `PATH`. Он не должен перезаписывать чужую установку или выдавать вывод версии SwiftPods за неизменённый upstream.

Декларация `plugin` сохраняется. Поддержка конкретных версий plugins публикуется в compatibility matrix. Отсутствующий plugin, конфликт dependency или неизвестный private hook являются диагностируемой ошибкой, а не причиной silently отключить plugin. CocoaPods plugins основаны на gems и входят в явный профиль окружения. [R11]

`ensure_bundler!` не превращается в безусловный no-op: запрошенная проверка либо реально выполняется в соответствующем окружении, либо явно сообщает, почему выбранный режим ей не соответствует.

## 10. Разрешение зависимостей и версии

### 10.1. Сохранение поведения

**SP-RESOLVE-001.** Первая версия использует resolver и правила сравнения версий базового Ruby-профиля. Новый solver нельзя вводить только потому, что он находит любое математически допустимое решение: выбранные версии, порядок источников и targeted update являются наблюдаемыми результатами миграции.

**SP-RESOLVE-002.** Сохраняются ограничения `=`, `!=`, `>`, `>=`, `<`, `<=`, `~>`, несколько одновременных требований, prerelease и версии с числом компонентов, допустимым в CocoaPods. Четырёхкомпонентные версии нельзя автоматически переписывать в трёхкомпонентные SwiftPM-версии.

**SP-RESOLVE-003.** Для `install` и `update` сохраняется различие из CocoaPods: установка опирается на lockfile, а явное обновление разрешает изменение соответствующих зависимостей. [R9]

При неизменном Podfile обычный `install` не ищет новые версии ради обновления. Изменённый Podfile разрешается по правилам эталона: нельзя обещать, что добавление зависимости никогда не потребует пересмотра графа или ошибки конфликта.

`update ExampleSDK` обновляет выбранную зависимость и связанную с ней часть графа по правилам профиля. Остальные изменения должны быть объяснены; команда не должна превращаться в незаявленное полное обновление.

### 10.2. Источники и идентичность

Источники spec-репозиториев обрабатываются в исходном порядке. Явный `:source` сохраняет ограничение поиска для данной зависимости. SwiftPods не добавляет свой публичный registry выше источников пользователя.

Внутренняя идентичность включает тип менеджера, происхождение/spec source, root pod, subspec и выбранную ревизию. Однако compatibility resolver сохраняет ограничения CocoaPods на использование одноимённых root pod из разных источников в одном графе; происхождение не становится способом незаметно установить две несовместимые копии.

Git branch/tag при установке связывается с конкретным commit. При существующем lockfile установка не должна автоматически следовать новому HEAD. Изменение зафиксированного происхождения или ожидаемого содержимого требует понятного отчёта.

### 10.3. Диагностика конфликтов

Сообщение должно содержать требуемые диапазоны, цепочки зависимостей, затронутые target/platform и доступное действие. Оно не должно автоматически повышать deployment target, исключать архитектуру или удалять транзитивную зависимость.

Пример формата, не реальный конфликт SDK:

```text
SP-RESOLVE-001: No compatible version of ExampleCore.

Game -> AdapterA 2.0 -> ExampleCore >= 5.0, < 6.0
Game -> AdapterB 3.0 -> ExampleCore >= 6.0, < 7.0

No version satisfies both requirements.
No project files were committed by this resolution step.
```

### 10.4. Deployment и offline

`install --deployment` запрещает изменения Podfile/Podfile.lock, которые несовместимы с режимом эталона. Локальная диагностика и установка отсутствующих файлов допустимы; скрытая повторная фиксация новых версий — нет.

`--offline` запрещает сетевой доступ управляемым загрузчикам и registry-клиентам SwiftPods. При отсутствующем объекте cache команда перечисляет, чего не хватает.

Этот флаг сам по себе не способен запретить сеть произвольному Ruby, `curl` из hook или другому внешнему процессу. Для гарантированного offline исполнения всего дерева процессов требуется внешняя изоляция CI/VM с запретом egress. Инструмент не называет обычный режим герметичным.

## 11. Lockfile, состояние и происхождение артефактов

### 11.1. Существующие файлы

`Podfile.lock` остаётся основным источником зафиксированных pod-зависимостей. Сохраняются стандартные секции, формат и порядок сериализации базового профиля. `Pods/Manifest.lock` отражает установленное состояние и должен соответствовать успешной установке. Эти файлы уже участвуют в работе CocoaPods. [R8, R12]

SwiftPods не вводит второй обязательный lockfile с альтернативными версиями тех же pod-зависимостей.

Для неизменного графа и совпадающего профиля повторная установка должна сохранять Podfile.lock побайтово. Изменение метаданных профиля при переходе между версиями показывается отдельно от обновления библиотек. В `--deployment` lockfile не переписывается ради имени нового инструмента.

### 11.2. Поле COCOAPODS и идентичность производителя

Поле `COCOAPODS` сохраняется как metadata референса совместимости для чтения стандартными инструментами; оно не означает загрузку или исполнение стороннего ядра. Фактический producer записывается в поле `SWIFTPODS`; версия и ревизия собственного движка дополнительно фиксируются в installation report и compatibility manifest.

Нельзя подставлять версию SwiftPods в это поле и сравнивать её как версию CocoaPods. Также нельзя использовать сохранённое совместимое значение как утверждение, что запускался немодифицированный upstream.

Legacy-референс использует в этом поле версию своего core; SwiftPods не выдаёт версию референса за версию собственного движка. Совместимое значение не является утверждением, что запускался немодифицированный upstream. [R12]

### 11.3. Собственное состояние

По умолчанию технические данные находятся в `.swiftpods/state.json` и могут быть пересозданы. Там хранятся профиль, producer, fingerprints управляемых файлов, журнал состояния и ссылка на последнюю установку. Эти данные не являются альтернативным resolver lock.

Для команд, которым нужна усиленная проверка содержимого, допускается opt-in `.swiftpods/Integrity.lock`, хранимый в VCS. Он содержит SHA-256 артефактов, происхождение, конкретные Git revisions и ссылку на digest Podfile.lock, но не выбирает другие версии pod.

Стандартные spec checksums не подменяются: checksum спецификации и checksum скачанного SDK — разные проверки. Дополнительная проверка не должна объявляться доказательством безопасности содержимого. [R12]

### 11.4. Воспроизводимость

Lockfile гарантирует не всё окружение. Для контролируемой воспроизводимости фиксируются версия инструмента/runtime, Swift toolchain, Xcode/SDK, gems/plugins, используемые входные файлы, требуемые ENV, commits и артефакты.

Произвольный Ruby и внешние scripts могут читать время, сеть или неучтённые файлы. Автоматическое обнаружение абсолютно всех таких входов не обещается. При неполном описании среды отчёт должен говорить об ограниченной воспроизводимости.

## 12. Xcode-интеграция

### 12.1. Имена и layout

Сохраняются `Pods/`, `Pods.xcodeproj`, `Target Support Files`, привычные xcconfig, module maps, script phases и workspace links. Если выбран `generate_multiple_pod_projects`, сохраняется соответствующая структура профиля.

Не нужно переименовывать `[CP]`-фазы в `[SP]` и каталоги `Pods-*` ради брендинга: имена могут использоваться пользовательскими скриптами. SwiftPods отмечает владение файлами в собственном состоянии, а не массовым переименованием.

### 12.2. Build settings

Сохраняются правила наследования и объединения настроек. Особое внимание уделяется `$(inherited)`, `OTHER_LDFLAGS`, `OTHER_CFLAGS`, `OTHER_CPLUSPLUSFLAGS`, header/framework/library search paths, C++ standard, Swift settings и пользовательским конфигурациям.

Существующие user xcconfig и base configuration references не должны безусловно заменяться. Если корректное подключение требует include-chain или изменение исходной генерации проекта, инструмент показывает конкретный конфликт вместо обещания успешной интеграции.

Запрещены глобальные «исправления» вида выставить всем pod один deployment target, отключить signing для всего приложения или удалить simulator architectures без явного запроса.

### 12.3. Бинарные SDK

Должны поддерживаться статические и динамические libraries/frameworks, XCFramework, ресурсы и зависимые системные frameworks в границах базового профиля и заявленной build-матрицы.

Выбор XCFramework slice учитывает не только CPU architecture, но и платформу/variant: device и simulator не взаимозаменяемы. Статическая библиотека не должна ошибочно встраиваться как динамический framework; динамические зависимости и resource bundles проверяются в итоговом приложении.

Обработка headers, module maps, Swift-generated Objective-C headers, embed/copy phases и signing выполняется без незаявленной смены правил сборки.

Privacy manifests и другие поставляемые ресурсы не должны теряться при упаковке. Наличие файла не является обещанием соответствия требованиям магазина; инструмент не генерирует фиктивные декларации поведения SDK.

### 12.4. Идемпотентность

Повторный install при одинаковых входах не должен дублировать build phases, references или ресурсы. Изменение локального состояния не оправдывает лишний diff в пользовательском проекте.

Если hook или внешний script намеренно пишет время или случайные значения, отсутствие diff не гарантируется. Такой случай диагностируется как недетерминированный вход, а не исправляется пропуском hook/script.

## 13. CMake и Mengine

Первый поддерживаемый сценарий — обычная интеграция с Xcode-проектом, созданным CMake:

```bash
cmake -S . -B build/ios -G Xcode
swiftpods install
```

Podfile указывает сгенерированный `.xcodeproj`. CMake остаётся владельцем исходного описания игрового проекта; SwiftPods владеет зависимостями и совместимой интеграцией после генерации.

**SP-CMAKE-001.** Поддерживаются C++17, Objective-C++, Clang modules, статические frameworks и требуемые linker flags без перевода Mengine на другую систему сборки.

**SP-CMAKE-002.** Повторная CMake generation обнаруживается по изменению управляемой части проекта; после неё install повторно и идемпотентно применяет интеграцию. Нельзя предполагать, что однажды изменённый `.pbxproj` останется неизменным после regeneration.

**SP-CMAKE-003.** Две системы не записывают `.pbxproj` одновременно. Автоматизация должна выполнять этапы последовательно; при обнаруженном внешнем изменении install не затирает его молча.

**SP-CMAKE-004.** Не заменяются существующие compiler flags и xcconfig пользователя. CMake предоставляет механизм установки Xcode attributes, но его документация предупреждает о последствиях низкоуровневого переопределения настроек; поэтому SwiftPods не должен автоматически переносить все настройки в такие overrides. [R14]

Полноценный CMake-native backend, экспортирующий зависимости как imported targets для разных генераторов, находится вне MVP. Это отдельная задача: ресурсы, embed/signing, Swift modules и произвольные Xcode hooks нельзя честно представить только набором include directories и library paths.

## 14. Сосуществование со SwiftPM

### 14.1. Первая версия

V1 сохраняет уже существующие SPM references и соответствующий `Package.resolved`; pod install не удаляет и не переписывает их. При этом SwiftPods не обещает общей нативной системы разрешения pod и SPM dependencies.

SwiftPM имеет собственную модель packages/products, правила версий и результат разрешения в `Package.resolved`; podspec не следует автоматически считать эквивалентным Swift package manifest. [R13]

Разные независимые SDK могут обслуживаться разными менеджерами. Один и тот же SDK и общий dependency subtree не должны незаметно устанавливаться дважды.

Проверяются известные package identities, modules, binary identities и explicit mappings. Найденный дубликат блокирует установку либо требует явного разбора. Отсутствие найденного дубликата не является доказательством отсутствия любых symbol collisions: разные упаковки могут скрывать одну библиотеку.

### 14.2. Дополнительный DSL после v1

Предлагаемая форма расширения остаётся Ruby:

```ruby
target 'Game' do
  pod 'ExampleLegacySDK', '~> 2.0'

  spm 'ExampleNetworking',
    :git => 'https://example.invalid/networking.git',
    :exact => '3.1.0',
    :products => ['ExampleNetworking']
end
```

`spm` — новый Ruby-метод SwiftPods, а не существующий метод CocoaPods. Он не нужен для миграции старого проекта. Добавив его, пользователь явно выходит за пределы двусторонне совместимого исходного Podfile.

Для SPM-части зависимости разрешает соответствующий Xcode/SwiftPM toolchain. Указываются product, target mapping и поддерживаемая форма version requirement. Неоднозначные версии и диапазоны не преобразуются по догадке.

В начальном SPM backend ссылки добавляются как native Xcode package dependencies. Они не изображаются обычными PodTargets: `installer.pods_project.targets` не должен создавать ложное ожидание, что пользователь может менять все SPM targets как CocoaPods targets.

### 14.3. Запрет неявного смешивания графов

`spec.dependency 'ExampleCore'` нельзя автоматически удовлетворить одноимённым SPM package. Для межформатных edges потребуется отдельный проверяемый bridge с правилами сборки, модулей и версий. До его реализации такой случай является ошибкой.

Автоматический переход pod → SPM из-за наличия Package.swift запрещён. Даже одинаковое имя или название вендора не доказывает идентичность версий, содержимого и поведения сборки.

## 15. Репозитории и публикация

### 15.1. Чтение

С первой версии поддерживаются стандартный CocoaPods CDN, Git spec repos, частные repos, локальные podspec и внешние sources базового профиля.

Новый центральный registry не является обязательным условием установки. После прекращения публикации в Trunk новые версии можно распространять через явно подключённые частные или публичные spec repos, не меняя язык podspec. [R1]

Доступность старого spec не гарантирует вечной доступности upstream-архива. Mirror хранит происхождение и проверяет целостность; пакет не должен подменяться другим содержимым под тем же именем и версией.

### 15.2. Публикация

Сохраняется привычная форма работы с собственным spec repo:

```bash
swiftpods spec lint GameCore.podspec
swiftpods repo push CompanySpecs GameCore.podspec
```

Registry для публикации выбирается явно. Команда, названная `trunk push`, не должна молча отправлять SDK в другой сервис или пытаться обходить read-only стороннего сервера.

Собственный публичный каталог — отдельный этап. Его обязательные требования: совместимые podspec, проверяемое владение именами, authentication, неизменяемые опубликованные версии, аудит изменений, понятная политика yanking, резервное копирование и переносимость.

Совпадение имени с pod из CocoaPods не даёт права присвоить его в новом registry. Перенос ownership и история происхождения проверяются отдельно.

### 15.3. Политика доверия к источникам

В compatibility-режиме сохраняется порядок sources. В hardened-профиле допускается требовать явную привязку приватных pod к registry, чтобы снизить риск получения одноимённой зависимости из чужого источника.

Изменение источника по сравнению с lock/integrity data показывается отдельно от изменения версии. Автоматическое добавление «более удобного» registry запрещено.

## 16. Безопасность и доверенное исполнение

### 16.1. Compatibility mode

Доверенные Podfile, Ruby podspec, gems, hooks и scripts могут выполнять произвольный код с правами пользователя. Отдельный Ruby-процесс облегчает управление жизненным циклом, но сам по себе не является security sandbox.

Инструмент явно обозначает эту модель. Нельзя рекламировать одновременно полную прозрачную совместимость с произвольным Ruby и гарантированный запрет любых его внешних действий без дополнительной изоляции.

CLI не запускается с root-правами для обычной установки. Credentials не включаются в lockfile, JSON-отчёты или cache keys. TLS-проверка не отключается ради автоматического исправления скачивания.

### 16.2. Hardened mode

Усиленный профиль включается явно и применяется до исполнения недоверенного входа. Он может запрещать Ruby podspec в пользу JSON, отключать execution hooks/plugins либо требовать изолированную VM/CI. Такой профиль намеренно не обещает полную совместимость с произвольным исходным Podfile.

Запрещённая конструкция вызывает отказ, а не успешный install без нужной части сборки. Ограничения профиля публикуются явно; их нельзя выдавать за полную совместимость с произвольным исходным Podfile.

`prepare_command`, build-time scripts и executable package plugins рассматриваются как отдельные поверхности выполнения кода. Hash checking не заменяет проверку доверия к издателю.

### 16.3. Дистрибутив и эксплуатация

Требуются подписанные release-артефакты, опубликованные SHA-256, закреплённые пользовательские gem-профили при их использовании, third-party licenses и процесс security updates. Ruby и его native dependencies обновляются их поставщиком; SwiftPods проверяет совместимость внешнего runtime. GitHub Releases и Homebrew tap публикуются отдельно. После `brew tap swiftpods-org/release https://github.com/swiftpods-org/swiftpods-release.git` и однократного `brew trust --formula swiftpods-org/release/swiftpods` в Homebrew 7 используется `brew install swiftpods`; установка без tap на чистой машине требует принятия формулы в homebrew/core. CI устанавливает конкретную версию с закреплённым digest release manifest/installer, выбирая подходящую macOS/architecture.

По умолчанию инструмент не отправляет пользовательские Podfile, исходники, список SDK или телеметрию во внешний сервис. Дополнительный сбор диагностики требует явного включения и возможности предварительно просмотреть содержимое.

## 17. Cache, производительность и восстановление

### 17.1. Cache

Первый стабильный cache предназначен прежде всего для metadata и скачанных неизменяемых исходных/binary-артефактов, а не для безусловного переиспользования любых результатов компиляции.

Объект адресуется digest содержимого и происхождением. Запись завершается атомарной публикацией готового объекта; незавершённый download не считается cache hit. Архивы проверяются на path traversal и небезопасные выходы за каталог распаковки.

Рабочие файлы, которые может изменить `prepare_command`, hook или внешний script, не должны быть writable hardlinks на общий cache. Используется независимая копия или корректный copy-on-write. Local development pod продолжает ссылаться на рабочую директорию пользователя по правилам эталона.

Новый SwiftPods cache результатов scripts/компиляции требует известных входов; при произвольных scripts такое дополнительное переиспользование по умолчанию отключено. Compatibility-профиль сохраняет prepared-source cache CocoaPods 1.17.0 и его правила вызова `prepare_command` как часть явно выбранного эталона, не объявляя это герметичным cache с полностью учтёнными входами. Hooks не пропускаются только потому, что Podfile.lock не изменился.

### 17.2. Измерения

Для каждого релиза публикуются результаты cold install, warm install, no-op install и targeted update на фиксированных fixtures с описанием машины, сети, cache и Xcode. Цель оптимизации — уменьшать лишние загрузки и файловые изменения, не меняя семантику.

Этот документ не утверждает конкретного ускорения. Обещания вроде «в десять раз быстрее CocoaPods» запрещены до воспроизводимых измерений.

### 17.3. Журнал и recovery

SwiftPods ведёт журнал изменений управляемых файлов, сохраняет их предыдущее состояние и использует process lock для собственных install-процессов. Изменение файлов внешней программой определяется перед перезаписью.

Отдельная запись управляемого файла должна быть атомарной там, где это возможно. Группа файлов, расположенных в разных каталогах, не объявляется одной атомарной filesystem-транзакцией.

При сбое применяется восстановление управляемых файлов либо выдаётся явный recovery state. Установка не помечается успешной до завершения требуемых этапов.

Нельзя гарантировать rollback сетевого запроса из hook, изменения файла за пределами учёта или любого внешнего процесса. Сохранение живых путей, наблюдаемых legacy hooks, важнее ложного обещания полностью изолированного staging для произвольного Ruby.

## 18. CLI и диагностика

Основная команда — `swiftpods`. Совместимые подкоманды первой версии сохраняют смысл соответствующих команд CocoaPods:

```bash
swiftpods init
swiftpods install
swiftpods install --deployment
swiftpods install --repo-update
swiftpods update
swiftpods update ExampleSDK
swiftpods outdated
swiftpods repo list
swiftpods repo add CompanySpecs https://example.invalid/specs.git
swiftpods repo update CompanySpecs
swiftpods repo push CompanySpecs GameCore.podspec
swiftpods spec lint GameCore.podspec
swiftpods lib lint
swiftpods cache list
swiftpods cache clean ExampleSDK
swiftpods deintegrate
```

`init` не перезаписывает существующий Podfile. `deintegrate` удаляет только распознанную pod-интеграцию; сторонние SPM references и пользовательские фазы не удаляются.

Дополнительные команды продукта:

```bash
swiftpods migrate --check
swiftpods doctor --static
swiftpods graph
swiftpods why ExampleSDK
swiftpods env import --gemfile Gemfile
swiftpods install --offline
swiftpods recover
swiftpods version --json
```

Все команды в документе являются проектируемым интерфейсом. Выполнение фактической установки или lint может исполнять Ruby, gems, hooks и внешние scripts и должно быть обозначено в help.

`graph` и `why` по умолчанию используют последний доступный installation report и показывают его актуальность. Они не должны незаметно выполнять неизвестный Podfile только ради просмотра. Получение свежего динамического графа запускается отдельным явно обозначенным режимом.

`doctor` сообщает о профиле окружения, conflicts, missing products/slices, повторном подключении SDK, несовместимом deployment target, потерянном наследовании build settings, недоступных артефактах и plugin compatibility. Непроверенные свойства имеют статус `unknown`, а не `passed`.

Для автоматизации поддерживается версионированный JSON-формат с кодом ошибки, этапом, файлом/строкой, dependency chain и последствиями для состояния проекта. Успех возвращает 0, ошибка — ненулевой exit status; точные совместимые коды baseline-команд закрепляются tests. Machine-readable diagnostic code не зависит от текста ошибки.

CLI не должен печатать секреты из ENV или URL credentials. Сообщение об ошибке hook содержит исходный Ruby backtrace с очищенными чувствительными данными. Ошибки внешних scripts содержат этап и exit status; machine-readable diagnostic code не зависит от текста Ruby-ошибки.

## 19. Тестирование совместимости

### 19.1. Differential harness

Одинаковая fixture запускается оригинальным CocoaPods выбранного профиля и SwiftPods в отдельных одинаково подготовленных средах. Сеть, доступный registry snapshot, Xcode, Swift toolchain, Ruby runtime, gems/plugins и входные файлы фиксируются. Эталон запускается независимо от движка SwiftPods; использование одного и того же ядра для обеих сторон не считается независимым сравнением.

Сравниваются выбранные версии и источники, target graph, build settings, файлы и module maps, содержимое ресурсов, порядок и результаты hooks и scripts, metadata lockfile, команды сборки и итоговая работоспособность.

Нормализация допустима только для заранее перечисленных несемантических отличий: например, корневого пути временной рабочей копии. Нельзя скрывать отличия порядка linker flags, удалять неизвестные поля из сравнения или считать сборку достаточной проверкой ресурсов.

Подтверждённые исправления ошибок и улучшения реализации учитываются отдельно от буквального совпадения. `Profiles/contract.json` задаёт политику `input_compatible` и тесты каждого заявленного улучшения: неизменённый вход и корректный эффект. Отчёт сохраняет наблюдаемое расхождение с референсом, но подтверждённое улучшение не блокирует приёмку. Отсутствующее доказательство совместимости входа или результата оставляет расхождение непроверенным. Требования к полному корпусу, целостности evidence и внешним проверкам сохраняются.

### 19.3. Покрытие и отчёт

Каждый метод/атрибут/опция базового DSL должен иметь traceability к тесту. Первая стабильная версия не объявляет весь DSL совместимым, если подтверждён только небольшой curated subset.

Для plugins и private API публикуется отдельный список подтверждённых версий, операций и ограничений. Проверяются hooks и сохранение внесённых ими изменений; наличие настоящего Ruby не заменяет эти tests. Отсутствие теста не обозначается зелёным статусом.

Реальные проекты, включая Mengine, добавляются как зафиксированные snapshots после получения доступа и разрешённых входных данных. Этот документ не утверждает, что их актуальные репозитории уже проверены или что все рекламные SDK уже собираются.

## 20. Этапы реализации

### Этап A. Основа совместимости

Фиксируются исходники и зависимости базового профиля, запускаются upstream suites и differential harness. Подготавливаются самостоятельное Swift-ядро и собственный DSL-адаптер с внешним CRuby. Референс и его gems изолируются от production-путей исполнения и упаковки. Проверяются отказ без совместимого Ruby, отсутствие встроенного интерпретатора, переносимость, release installer и Homebrew tap.

Результат: экспериментальный `swiftpods install`, использующий оригинальные Podfile/podspec и живую Ruby-объектную модель. Это ещё не основание обещать stable compatibility.

### Этап B. Стабильная версия 1.0

Включает весь заявленный baseline DSL, существующий Podfile.lock, основные CocoaPods CLI workflows, CDN/Git/private repos, source и binary pods, hooks, документированный plugin profile, Xcode-интеграцию, CMake-generated Xcode scenario, диагностику, cache и recovery.

Existing SPM dependencies сохраняются, но новый SPM DSL не требуется. Новый публичный registry также не является условием выпуска.

Результат: миграция поддерживаемого pure-pod проекта заменой команды, без переписывания dependency manifests и hooks. Для Bundler/plugins предусмотрен явный импорт окружения; внешние ограничения и непроверенные интеграции показываются в migration report.

### Этап C. SwiftPM backend

Добавляется opt-in Ruby-метод `spm`, native Xcode package integration, работа с Package.resolved и проверка известных duplicate SDK. Межформатные зависимости не эмулируются без отдельной спецификации bridge.

### Этап D. Инфраструктура развития

Возможны публичный registry, SDK compatibility catalog, проверенный binary build cache, полноценный CMake backend и дополнительные native-компоненты ядра.

Ни одна из этих функций не меняет существующий Podfile автоматически. Публикация SPM-only или CMake-native режима сопровождается собственной матрицей совместимости.

## 21. Критерии приёмки версии 1.0

**AC-001.** Поддерживаемый контрольный проект переходит с `pod install` на `swiftpods install` без редактирования Podfile и podspec.

**AC-002.** Подключённые helper Ruby-файлы и legacy hooks работают без переписывания в поддерживаемом профиле; изменения Xcode project objects сохраняются в правильный момент. Это подтверждается differential tests, а не только наличием runtime.

**AC-003.** При неизменных manifest и lock не происходят незаявленные обновления версий или переключение sources.

**AC-004.** Результат собирается и проходит контроль ресурсов/линковки на опубликованной матрице Xcode и платформ.

**AC-005.** Повторная установка идемпотентна для детерминированных fixtures; CMake regeneration корректно обрабатывается повторным install.

**AC-006.** Стандартная поставка не содержит Ruby runtime. Внешний CRuby выбирается явно или по документированным правилам, version/ABI/architecture проверяются до проектного кода и journal. Собственное Swift-ядро и Ruby DSL-адаптер работают после переноса; installer проверяет SHA-256 и совместимость OS/architecture, сохраняет чужие destinations. Homebrew устанавливает Ruby отдельной зависимостью. Дополнительные plugins проходят отдельную проверку.

**AC-007.** Existing SPM dependencies не повреждаются. Обнаруженные дубликаты SDK и конфликты не исправляются скрытым удалением зависимости.

**AC-008.** Неподдерживаемые или непроверенные возможности явно обозначаются. Запрещены no-op реализации обязательных DSL-конструкций ради успешного выхода.

Подтверждённые улучшения согласно SP-COMPAT-006 допускаются в стабильном релизе. Критерий совместимости — сохранение входного контракта и корректный результат; воспроизведение ошибок референса не является критерием приёмки.

**AC-009.** Сбой не оставляет ложного успешного состояния; доступны восстановление управляемых файлов и отчёт об ограничениях rollback.

**AC-010.** Pure-pod проект без SwiftPods-only расширений сохраняет возможность возврата к исходному CocoaPods workflow; это подтверждено тестом, а не предполагается по сходству YAML.

## 22. Зафиксированные архитектурные решения

**ADR-001: настоящий Ruby устанавливается отдельно.** Решение 0.7 отменяет встроенный runtime из 0.4. SwiftPods запускает внешний CRuby и сохраняет оригинальный DSL, реальную Ruby-объектную модель и hooks. Интерпретатор на Swift не создаётся.

**ADR-002: независимое Swift-ядро.** Resolver, источники, кеш, lockfile, модель и генератор Xcode реализуются на Swift. Внешний CRuby выполняет пользовательский DSL, helpers и hooks через собственный адаптер. Референс используется только в изолированных differential tests и не поставляется. Совместимость входных данных и корректность результата подтверждаются отдельными fixtures.

**ADR-003: не заменять Podfile.lock новым resolver lock.** Дополнительные integrity metadata не выбирают версии pod.

**ADR-004: сохранить живые Ruby project objects.** В одной команде один долгоживущий Ruby Host; существующие hooks работают с реальными installer/target/project objects. IPC не заменяет эти объекты JSON-копиями.

**ADR-005: SwiftPM — дополнительный backend, не скрытая миграция.** Pod dependency и Swift package не считаются взаимозаменяемыми по имени.

**ADR-006: CMake сначала через существующий Xcode workflow.** Полноценный native backend не выдаётся за решённую задачу одной генерацией include/link flags.

**ADR-007: совместимость и изоляция — разные профили.** Полный произвольный Ruby не называется безопасным sandboxed DSL. Ограничения hardened-профиля применяются до исполнения.

**ADR-008: измеряемый критерий успеха — сохранение проекта.** Принятие исходного текста, выбранные зависимости, hooks, build outputs и возврат к старому workflow важнее доли кода на Swift.

**ADR-009: совместимые входы, самостоятельная реализация.** SwiftPods не наследует ошибки CocoaPods. Более простые алгоритмы и улучшенные результаты допустимы при сохранении входного контракта; каждый обнаруженный эффект проверяется и фиксируется без скрытого объявления буквального совпадения.
