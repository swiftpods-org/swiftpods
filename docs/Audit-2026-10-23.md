# Ten confirmed regression contracts

The audit at `d0c30ad` introduced ten active regression tests in `30a299f`.
The subsequent repair corrects all ten defects described below. The tests remain
active; no expected-failure decorators, warning suppression, or CI failure bypass
is used.

The findings below describe the implementation before repair. The tests exercise
macOS Xcode projects and real SDKs; they do not establish device, release-package,
or published-version acceptance.

| ID | Priority | Defect and reproducer | Cause |
| --- | --- | --- | --- |
| 1 | P1 | With multiple pod projects, `project_name: 'pods'` aliases the aggregate `Pods.xcodeproj` on a case-insensitive volume. Installation writes the child project and then fails with `SP-XCODE-CONFLICT`, leaving recovery required. It should reject the project-name collision before these writes. `Separate` is a building control. | [NativeProjects.swift:27](../Sources/SwiftPodsCore/NativeProjects.swift#L27) checks only the exact spelling `Pods`. |
| 2 | P1 | Configurations `Debug` and `DEBUG` receive the same support xcconfig reference. Writing different settings for the second configuration overwrites the first configuration's file. Xcode's own `-showBuildSettings` distinguishes both names before installation. | [NativeXcconfig.swift:140](../Sources/SwiftPodsCore/NativeXcconfig.swift#L140) lowercases configuration names in support filenames. |
| 3 | P2 | Two distinct, explicit maps declaring `Feature` and `feature` are rejected as a module conflict. A strict Clang probe successfully imports both modules and reads both APIs. Their physical map/header directories differ. | [NativeModuleProducts.swift:109](../Sources/SwiftPodsCore/NativeModuleProducts.swift#L109) folds Clang module identifiers to lowercase along with framework products. |
| 4 | P2 | Two binary-only pods whose distinct SDK products declare the same module `Shared` install successfully. The shared public module namespace should be rejected before consumer/lockfile writes. Two SDKs with distinct modules build and run in Debug and Release. | [NativeModuleProducts.swift:118](../Sources/SwiftPodsCore/NativeModuleProducts.swift#L118) skips binary-only consumers; the later loop also compares vendors only with source module owners. |
| 5 | P2 | A binary-only pod can also export an explicit `module_map`. When its facade and a source pod both declare `Shared`, installation accepts the conflict. A facade called `BinaryAPI` builds and runs successfully. | [NativeModuleProducts.swift:164](../Sources/SwiftPodsCore/NativeModuleProducts.swift#L164) returns before inspecting the binary pod's explicit facade map. Header generation still exports that map to consumers. |
| 6 | P2 | A `before_headers` script is placed after a mapped header copy phase whose destination uses `${PUBLIC_HEADERS_FOLDER_PATH}`. The equivalent `$(PUBLIC_HEADERS_FOLDER_PATH)` works and remains stable on deployment reinstall. | [NativeScriptPhase.swift:101](../Sources/SwiftPodsCore/NativeScriptPhase.swift#L101) recognizes only the parenthesized suffix when locating copy phases. |
| 7 | P1 | `lib lint` accepts a corrupted Swift module in a versioned macOS framework whose root `Modules` is a symlink. The same valid framework passes both direct Swift typechecking and lint; after corruption Swift rejects it while lint still reports `passed` with no warnings. | [NativeLintVendorInterface.swift:21](../Sources/SwiftPodsCore/NativeLintVendorInterface.swift#L21) lists the unresolved `Modules` symlink and fails to generate the Swift import probe. |
| 8 | P2 | An authored map starting with `/* authored */ framework module Kit ...` fails a static-library consumer build with `Header 'Kit.h' not found`. Removing the leading comment yields successful Debug/Release builds. The authored bytes must remain unchanged. | [NativeLibraryHeaders.swift:71](../Sources/SwiftPodsCore/NativeLibraryHeaders.swift#L71) strips the `framework` qualifier only at the beginning of a line. |
| 9 | P2 | Reordering Podfile user script phases from `[A, B]` to `[B, A]` and reinstalling still executes `AB`. The regression builds the app before and after the change and checks the scripts' output. | [NativeScriptPhase.swift:91](../Sources/SwiftPodsCore/NativeScriptPhase.swift#L91) updates existing phase objects without applying their new declaration order. |
| 10 | P2 | A concrete parent exports `Other` through `inherit! :search_paths`; a child links `Kit`. If both declare `Shared`, installation accepts the conflict even though the child receives both interfaces. A distinct-module parent/child control builds and runs. | [NativeModuleProducts.swift:80](../Sources/SwiftPodsCore/NativeModuleProducts.swift#L80) validates linked dependencies but omits search-only dependencies. |

## Coverage and reproduction

[NativeAuditCoverageTests.swift](../Tests/SwiftPodsCoreTests/NativeAuditCoverageTests.swift)
adds one focused Swift test for each finding. The support-file test checks both
file identity and preservation of the first file's bytes, giving 11 failing
assertions across ten test methods in the original audited implementation.
Six additional controls now cover configuration alias reservations, SDK sharing,
consumer/configuration isolation, module-map token preservation and script ordering
around unrelated user phases, including Swift module output filename collisions.

[audit_coverage_regressions.py](../Tests/Regression/audit_coverage_regressions.py)
adds ten integration scenarios and working controls. It exercises actual CLI
installation, offline deployment reinstallation, generated project references,
Clang imports, real binary SDKs, Debug/Release application builds and execution,
Swift typechecking, lint, and script execution. The header-position scenario
checks generated phase ordering for both supported variable syntaxes. Each case
records its result before proceeding; `audit-coverage.json` and
`audit-controls.json` survive failures in the owned verification workspace.

Run from the repository root:

```sh
python3 -m Tests.swift_tests
python3 -m Tests.Regression.audit_coverage_regressions
python3 -m Tests.Regression.module_ownership_regressions
python3 -m Tests.Regression.header_namespace_regressions
```

The new matrix belongs to the full native lifecycle suite and the Build SwiftPods
workflow on both configured macOS architectures. Its CI step runs even when the
unit step fails, so known unit failures do not hide the integration diagnostics.
Any assertion failure still prevents successful packaging.

## Validation boundary

The original frozen audit run contained 941 Swift tests: the 931 existing tests
passed while the ten new methods failed (11 assertions, zero unexpected failures).
The integration matrix reproduced all ten corresponding failures.

After repair, the frozen verification runs all 947 Swift tests and all ten audit
integration cases successfully. Existing header namespace and module ownership
matrices also pass, along with targeted header/path, variant, subspec, vendor and
lint regressions. Compiler warnings remain failures. Rejected conflict fixtures
and the intentionally corrupted Swift module are successful negative checks.
The local runs do not substitute for the remote CI architecture matrix.

## Repair behavior

- Project paths are validated with case folding before writing child projects.
- Colliding configuration spellings receive deterministic, reserved aliases;
  conventional `Debug` and `Release` include filenames remain available.
- Module identifiers retain case; generated Swift module filenames retain filesystem
  collision checks. Binary-only facades and inherited compiler
  interfaces participate in ownership checks. Binary ownership is tracked per
  consumer, configuration and build destination, with repeated SDK URLs deduplicated.
- Header copy anchors accept both Xcode variable syntaxes. Reordered scripts keep
  declaration order within their execution position, preserving unrelated phases.
- Lint resolves versioned framework directories before enumerating Swift modules.
- Static-library map conversion changes declaration tokens while preserving
  comments, quoted text, link directives and the original authored file.
